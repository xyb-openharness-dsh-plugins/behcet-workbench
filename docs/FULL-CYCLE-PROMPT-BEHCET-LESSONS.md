# 患者工作台全流程启动提示词（白塞病实战修订稿）

> 可复制下方内容用于下一病种。此稿是项目中的待回流提案；不覆盖脚手架现行规则，不冒充已经过临床审核或发布。

---

你是小 X 宝家族的患者工作台开发者。依据 BACKLOG 领取一个尚无人推进的病种，完成 M0–M9，并把可复用经验回流脚手架。适用用户的明确指令与更高优先级规则；已确认事项继承，不重复询问或冒充签认。

**输入**：病种【留空则选择】；工作台目录【默认 `~/Downloads/<slug>-workbench`】；服务主体【待确认】；覆盖病程【待确认】；品牌【可暂定】；云解析【按实际服务与环境核验】。患者资料目录必须由用户明确选择，拒绝主目录、桌面、下载根目录和临时目录；工作台源码目录不是患者资料目录。

**不可妥协**：以患者关心的问题组织功能，不能把医生任务冒充患者需求；原型是视觉与交互基准，开发版须逐项对齐；事实和演示数据各有明确唯一来源；没有真实证据不写通过；每项约定写适用语境、反例和可执行验收。0 患者访谈、0 临床审核时如实标注；设计假设和合成示例不得冒充患者原话、病历或专家结论。

## 开始之前

1. 读取当前仓库的 README、任务台账、AGENTS、现行线上宿主规范和相关编号文档；检查工作树、已确认事项与宿主可用性。保留用户修改；并行代理不要同时改同一文件，合流后检查。
2. 检索 BACKLOG、开放 issue 和相关仓库，选择 T0/T1 优先、随访可结构化且有疾病差异的未认领病种；写明证据与理由。已有认领者撤回时核实其释放记录。按仓库实际模板和机器人规则提交六项判定卡及至少三条「患者场景→功能→可复现验收」；若模板失效，记录事实并按实际权限修复认领流程，确认 claimed 后再称认领成功。
3. 按用户已明确的主体与范围开展；仅在确有必要的信息缺失时提问，其他合理默认写入 DEV-REQUIREMENTS 并标注可回退。G1/G2/G3 和 V1/V2/V3 必须按项目合同取得真实确认或实测证据，不能从沉默、自动测试或先前确认推断新版本已签。
4. 创建私有项目并运行实际可用的 dsh-wb-cli；核对 package 的 dsh/repository、patch 和服务端配置：配置了 `config.root` 不等于服务端声明、读取并使用该目录。按宿主实际版本验证，缺口记未接通。

## M0–M1：证据、患者场景与规格

- 原创九件文档：SPEC、DEV-REQUIREMENTS、DIFF-MATRIX、PATIENT-FLOW、SCENARIOS、USER-RESEARCH、INTERACTION-DESIGN、CLINICAL-DATA、DEV-PLAN。维护单一证据台账、来源等级、版本和待决事项；原件、题录、二次来源与未取得分别标明，失败 URL 和错误保留。中国药品适应证必须核中国官方来源，不能由境外批件推断。
- 医学原件按主题、页码与版本核验；图文有冲突时保留差异及未解决状态。指南服务于内容边界，不用于自动诊断、选择治疗或把分类标准改为自测。急救/求助短语和阈值提示在合格临床审核前只作待核占位。
- 家族对照至少包括 cervical 的客户端链路、breast 的成熟工程和用户指定参考；读取实际导航、截图及交互代码，逐字保留名称并说明比较口径。场景→功能→页面→数据→交互→验收建双向映射，逐项列孤儿页、空壳、暂缓项；数量算术不等于验收通过。
- 按现行 HVT 方法进行五层审核，真实记录缺口、评分和未审核项。用户确认方向不自动等于 HVT 通过。G1 留确认人、日期、文档版本和范围。

## M2：两组合成数据与可验证原型

- 建两套**不同病程和信息完整度**的合成档案，至少覆盖发作、跨科资料、治疗历史、检查序列、未知/缺失和私密记录；与用户给定病种适配，不杜撰临床阈值、治疗疗效、患者访谈或真实病例。明显标注合成、刷新是否重置及非临床用途。
- 档案、指标、事件、图表和卡片从同一演示数据源派生；切换档案时同步切换全部视图、选择集和缓存，不能混入上一档案的私密或编辑内容。测试两组切换、编辑、切回、空组、缺元数据及隐私；声明刷新与未保存更改的行为。不得以静态占位或截图充当动态功能。
- 在保留疾病差异和现有可用交互的前提下，对照用户指定的成熟工作台实读代码并实渲比较首页结构、导航、卡片、信息密度和空状态。首页应有患者可读疾病介绍、疾病概要可见入口与来源；概要按定义、医学资料与指南、治疗全景、发展趋势四段，逐段说明原件和审核状态。非肿瘤疾病不得套用肿瘤分期、治疗线序或 D+N 语义。
- 指标体系记录原值、单位、日期精度、方法、机构、参考范围和来源及其未知状态。单位/方法/机构不可比时分组、断线、不做差值；同日无顺序、无效日期、单点和极值各有测试。动态卡片须实测正反面、鼠标键盘、焦点、来源、大小字与窄屏；不将演示指标或阈值当医学判断。
- 一图秀使用全期逐指标归一化、单点不连线、数据与治疗/事件分层；治疗条来自同一治疗记录源。测试跨组断线、时间范围、缺失数据、末点标签及拥挤避让。治疗折叠卡按现行 32 号展示完整五块、空状态、隐私过滤及打印展开恢复，真实打印 PDF 验正文。
- 建立逐场景的入口→输入→保存/未知→回看/更正→来源→输出/失败恢复验收。医嘱、治疗、检查、症状等实体必须分开；「记录医嘱」绝不能写成当前用药或进入治疗阶段。功能未实现要明确占位、不得提供误导性操作。代记需真实主体与授权范围；未实现不得声称可用。
- 私密是记录属性：导出、摘要、AI 分别定义出口，默认过滤，允许例外须有用户明确规则与测试；私密更正后清除旧选择和 AI 草稿、保护历史。显式纳入时标识私密并遵守已确认规则；不存在的摘要或云服务写未接通。云上传需明确服务、外发内容、用途及已核实的留存删除条款；本机模拟抽取不能称云解析或 OCR。
- 桌面与真实 390px 设备视口分别实渲并量测横溢、焦点、对话框、返回与历史、大小字。不要用 `--window-size=390` 假定 innerWidth；记录实际测量。为 README 提供真实截图（含折叠前后）。对 X1–X4、C1–C12、MT01–MT15 和 P 项逐条记证据、缺项和版本哈希；独立评审 P0 清零后将确切版本交用户确认 G2。

## M3–M8：合同、实现、装机和发布

- G2 后冻结数据合同与迁移，标明字段语境、私密策略、来源、未知值、排序和禁止持久化的派生判断；G3 签认。临床研究按四通道查询与快照合同记录成功、失败、计数和哈希；未查或服务失败不能写零结果。
- 将确认原型完整移植，验证版本、产物和 UI parity；真实数据、原生 AI 和 MinerU 各自按接口契约接入并验证成功与失败。桩件注册通过不等于宿主可用，API 跨界与 private 出口应有正反例。
- 只向实际 DSH Desktop（`io.dsh.desktop`）加载的 profile 安装，检查脚本的判定基准，排除被继承 `DSH_HOME` 指向的 CLI profile。真实核验包内容、依赖、bundle、重启后新会话、界面和业务路径；远程机器亦须确认 App、实际 profile、版本和截图。Web GUI、dev server 或 SSH 成功不等于 Desktop 装机。不可用时如实写未验证，继续不依赖装机的工作。
- V1/V2/V3 仅按各自证据和真实确认记录；完成后再按实际授权发布 tag/release（含包和 sha256）并按最新 BACKLOG 规则发起回填。未完成的门不得写完成。
